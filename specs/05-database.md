# 05 Database

SQLite foundation: connections, schema, migrations, and two databases — `app` (application data) and `audit` (query log, [07](./07-audit-logging.md)).

App schema to support (columns are a starting point, not a contract):

- `user` — contact (erased on closing unless banned, [08](./08-auth.md)), created by, soft-delete (closed at/by/reason)
- `user_profile` — 1:1 with user, created on onboarding (birth date)
- `user_role` — role, assigned by, soft-delete (revoked at/by/reason); one active row per user and role
- `user_session` — secret hash, created/expires at, IP, soft-delete (revoked at/by/reason)
- `login` — contact, optional user, code hash ([08](./08-auth.md)), expires at, IP, send ID
- `login_attempt` — success flag, attempted at, IP

## Ideas

- Soft-delete column groups stay consistent via `CHECK` constraints.
- Filtered unique indexes for "one active row" rules.
- One drizzle-kit config per DB, environment chosen by mode.
- Decide whether the template ships app migrations or lets each project generate the first one.

## Checklist

- [x] All connections share one factory: busy timeout (concurrent processes wait instead of failing), WAL.
- [x] Schema conventions (naming, soft delete, constraints, indexes) are consistent and documented.
- [x] Generate/migrate scripts exist per DB and environment; production migration reads production env.
- [x] Connections close on `sveltekit:shutdown`.
- [x] Drizzle query errors never expose query params in messages or `inspect()` output — tested. (Drizzle includes them by default; find the lightest fix.)

## Decisions

- drizzle-kit configs: one per database, `cli/db/drizzle-kit/[database].ts`. Each is one line calling `defineDatabaseConfig(database)` (`cli/db/drizzle-kit/config.ts`), which reads the mode from `MODE` (required, one of `development`, `e2e`, `production`, so a typo can't create a new data directory), loads the mode's env files with `process.loadEnvFile` (highest precedence first, since it never overrides), parses `DATA_DIR`, builds the path, and creates its directory. drizzle-kit has no `--mode` or `--env-file` flag ([drizzle-team/drizzle-orm#4588](https://github.com/drizzle-team/drizzle-orm/issues/4588)), so scripts prefix `MODE=[mode]`, once per `&&` command; `vpr` applies the prefix itself, so it works on Windows ([voidzero-dev/vite-plus#3140](https://github.com/voidzero-dev/vite-plus/issues/3140)). The repo requires Vite+, so `pnpm run` on Windows isn't supported. It's the one CLI exception that reads env files in TS ([02](./02-cli-separation.md)). drizzle-kit also loads `.env` into `process.env` before its config runs ([v0.20.0](https://github.com/drizzle-team/drizzle-kit-mirror/releases/tag/v0.20.0)), so `.env` values outrank `.env.local` and `.env.[mode]`. Accepted: don't set `DATA_DIR` in `.env` (noted there). Rejected: a custom env file reader that worked around this. Rejected: one config per database and mode (`[mode].[database].ts`, five files). No `strict`: since rc.5, `push` rejects it in favor of `--explain` (a dry run), so `db:push` applies without asking (development only).
- Layout: `src/db/[database]/` per database, split by who may import it: `enums/` is client-safe (UI labels, form validation), `server/` is server-only (schema, clients, procedures). SvelteKit 3 enforces it: any `server` directory outside `src/routes` is server-only, so client code importing `#db/app/server/…` fails the build ([server-only modules](https://svelte.dev/docs/kit/server-only-modules)). Code shared by both databases (connections) is one file, `src/db/shared.server.ts` (server-only by its `.server` segment), tested in `src/db/shared.test.ts`. The import path shows database and side, e.g. `#db/app/enums/user.ts`, `#db/app/server/procedures/user.ts`. Rejected: `src/db/server/[database]/` (enums would need a second tree); `src/db/server/shared.ts` (a directory for one file).
- Migrations: `drizzle/app/` and `drizzle/audit/`. Schemas: `src/db/app/server/schema.ts` and `src/db/audit/server/schema.ts` (empty until [07](./07-audit-logging.md)), each re-exporting one file per table name prefix from `schema/` (e.g. `schema/user.ts` holds `user`, `user_profile`, `user_role`, and `user_session`).
- Scripts: `db:generate:app`, `db:generate:audit` (generate doesn't connect, so any mode's config works; audit uses `e2e`, since development has no audit database and `production` would load `.env.production` and create `data/production/` locally); `db:migrate:[mode]` migrates every database of the mode; `db:push` and `db:studio` are development only.
- The SvelteKit client (`src/db/app/server/client.ts`) opens `:memory:` while `building` (build analysis and prerendering), so `vpr build` creates no files, e.g. no `data/` in the image ([12](./12-operations.md)). Prerendered pages can't read the database.
- Connections: `openDatabase(path)` (`src/db/shared.server.ts`) sets a 5-second busy timeout and WAL. Foreign keys and the defensive flag are already `node:sqlite` defaults. The SvelteKit client and unit tests use it; the CLI client will ([02](./02-cli-separation.md)). drizzle-kit opens its own connection: WAL persists in the file, but there's no busy timeout, so migrate while the app is stopped ([12](./12-operations.md)).
- Shutdown: the SvelteKit client closes on `sveltekit:shutdown`, which adapter-node emits after the HTTP server closes. Verified by hand (build, request, SIGTERM, `isOpen` is `false`). A missing listener can't be caught by checking `-wal` files: Node.js also closes databases at exit. Dev and preview don't emit it; dev skips the listener, since each module reload would add one and keep the old connection alive.
- Query errors: Drizzle 1.0.0-rc.5 leaves params out of `DrizzleQueryError` unless `paramsInErrors` is set ([drizzle-orm#5939](https://github.com/drizzle-team/drizzle-orm/issues/5939)); never set it. Tested in `src/db/shared.test.ts` (prepare and run failures, via `inspect()`), so a regression fails on upgrade. The SQL text stays (values are bound, unless `sql.raw` is used), and `node:sqlite`'s `cause` holds no values.
- Schema conventions (`src/db/app/server/schema/`):
  - Tables use `snakeCase.table` (Drizzle 1 casing lives in the schema, so the runtime and drizzle-kit can't disagree): singular snake_case table names, camelCase keys, snake_case columns. Exports are the camelCase table name plus `Table` (`userTable`, `userSessionTable`), so rows get the plain names (`const user = …`, `login.id`). Relational query keys follow the exports (`db.query.userTable`). Rejected: bare names (`user`), which took the row's name, and mapping relation keys back to bare names in `defineRelations` (a hand-kept list). Each table also exports `[Name]Insert` and `[Name]Select` (`$inferInsert`, `$inferSelect`); fixtures `satisfies` `Insert`, and procedures type their parameters from `Select` ([06](./06-query-layer.md)).
  - IDs are `integer().primaryKey({ autoIncrement: true })`, so deleted IDs are never reused, as with PostgreSQL sequences and MySQL 8's `AUTO_INCREMENT`. Purged rows (`login`, `login_attempt`, `user_session`) would otherwise give their IDs to new rows, and audit entries that outlive them would point at the wrong row ([07](./07-audit-logging.md)). One rule for every table, so a table that starts being purged can't miss it. Rejected: `AUTOINCREMENT` only on purged tables, as [SQLite advises](https://www.sqlite.org/autoinc.html) (the overhead is negligible here). 1:1 tables use the parent's ID as primary key (`user_profile.user_id`).
  - Timestamps are `[verb]At`, `integer({ mode: 'timestamp_ms' })`, without SQL defaults: procedures pass the time they read inside the transaction ([06](./06-query-layer.md)).
  - Actors are `[verb]By`, a nullable FK to `user`: whoever acted, including the user themselves (logout sets `revokedBy` to the session's user). `null` means the system (CLI, expiry), or no user yet (self sign-up's `createdBy`). Cascades copy the triggering actor (an admin closing a user is also `revokedBy` on the cascaded revokes).
  - Soft delete is a `[verb]At`/`[verb]By`/`[verb]Reason` group with two `CHECK`s: `Reason` is set exactly when `At` is, and `By` requires `At`; `Reason`'s prefix matches `By` ([08](./08-auth.md)). Like Laravel's `deleted_at`, but with domain verbs, and the actor kept in the row: audit entries are purged after 2 years and live in another database ([07](./07-audit-logging.md)). Every group is final: a closed user, revoked role, or revoked session is never reopened, so rows keep their history (a new grant is a new row). Procedures enforce it: they update only rows whose `At` is still null ([06](./06-query-layer.md)). Rejected: a `BEFORE UPDATE` trigger per group (Drizzle can't declare triggers, and drizzle-kit doesn't track a custom migration's triggers when the first migration is regenerated). Temporary suspensions, if needed, get their own table. Finished `login`, `login_attempt`, and session rows are hard-deleted by a purge job, since they hold personal data ([12](./12-operations.md)).
  - "One active row" rules are filtered unique indexes (`WHERE revoked_at IS NULL`).
  - Enums (roles, reasons) are TS-only (`text({ enum })`): a `CHECK` would need a table rebuild for each new value. The lists live in `enums/[prefix].ts` (e.g. `src/db/app/enums/user.ts`) as `as const` arrays with derived types, so Drizzle, Valibot (`v.picklist`), and UI labels share them. A column's full list is built from partial ones: what callers pass (`userRoleRevokeReasons`), plus the `cascade_` values only procedures write (`userRoleRevokedReasons`). `CHECK`s that depend on enum values match a prefix with `GLOB` (case-sensitive, `_` is literal), not a value list, e.g. `closed_reason NOT GLOB 'admin_*' OR closed_by IS NOT NULL`, so a new value that follows the naming convention needs no migration ([08](./08-auth.md)). Cheap value checks are `CHECK`s: date format (`x IS date(x)`), hash length, expiry after creation, soft delete not before creation.
  - Constraint and index expressions use Drizzle's operators (`gt`, `and`, `isNull`, …); `sql` only where none exists (`length()`, `IS date()`, `GLOB`) or where it would bind a value (`eq(x, 'a')` renders `?` in the migration). `and()`/`or()` return `SQL | undefined`, so checks assert them (`!`). The soft delete `CHECK`s come from one helper, `softDeleteChecks` in `src/db/app/server/schema/checks.ts`, so every group applies them the same way.
  - Foreign keys don't cascade: a delete that spans tables is a procedure that deletes children first, shared by SvelteKit and CLI ([06](./06-query-layer.md)). Each table's delete is its own statement, so the audit log shows every table it touched ([07](./07-audit-logging.md)). Rejected: `ON DELETE CASCADE` (rows vanish without their own audit entry, and the rule hides in the schema).
  - Names: `[table]_[columns]_idx`, `[table]_active_unique`, `[table]_[rule]_check`; foreign keys keep Drizzle's names. Foreign key columns get an index where they're looked up.
  - `user.contact` is unique across all users, closed included, so a banned user's contact can't sign up again until the block period ends. Other closings erase it at once, after which it can ([08](./08-auth.md)). It's nullable, but only on closed users (`user_contact_check`); `UNIQUE` ignores nulls. Normalizing it is [08](./08-auth.md)'s job too.
  - ESLint's `perfectionist/sort-objects` is off in table files (`src/db/*/server/schema/*.ts`), so columns stay in table order.
  - Each schema file has a test file next to it (`schema/user.test.ts`), with a `describe` per table, that tests its constraints on an in-memory database with the migrations applied (`createTestDatabase`, `src/db/app/server/testing.ts`). Shared checks (`softDeleteChecks`) get their full case matrix on one table (`user`); other tables test only that they apply them. Rejected: a `checks.test.ts` on a test-only table (not in the migrations, so it needs handwritten DDL or drizzle-kit at test time, and still misses a table that forgets the helper).
- The template ships the app's first migration (`drizzle/app/[timestamp]_init/`), so E2E and a fresh deployment work out of the box. A project that changes the starter schema before its first deployment can delete `drizzle/app/` and regenerate.
