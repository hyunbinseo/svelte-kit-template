# 06 Query Layer

How routes, remote functions, and CLI scripts reach the database. This is the most open spec.

## Ideas

- Audited reads as a per-call or per-module choice.
- Enforce "sync transaction callbacks" with types.
- Domain verbs for names (`find`, `create`, `claim`, `mark`, `link`, `discard`, `grant`, `revoke`) over SQL verbs.

## Checklist

- [x] Transactions reject async callbacks (type error). `node:sqlite` is sync; an async callback would commit early.
- [x] Read-then-write paths run in `immediate` transactions.
- [x] Multi-row invariants (e.g. closing a user revokes their roles and sessions; granting a role requires an active user without it) live in procedures shared by SvelteKit and CLI.
- [x] Deletes that span tables keep their order (children first) in one query file, e.g. `login/queries.ts` deletes attempts before logins when closing a user ([08](./08-auth.md)).
- [x] Each procedure runs in one transaction, reads the clock inside it, guards every row it depends on, returns falsy on no-op — and each guard is tested.
- [x] SvelteKit server modules (remote functions, server hooks, server endpoints, server load functions) and procedures don't build queries. They call named queries from query files, and ESLint enforces it.
- [x] Queries are plain functions taking the database first, `findActiveUser(db, { userId })`, placed by the tables they act on: each prefix folder's `queries.ts` (`user/queries.ts`), or one route's in a `queries.server.ts` next to its remote file.
- [ ] Reads are not audited by default; a route can opt in ([07](./07-audit-logging.md)).
- [x] Drizzle's sync API is used.
- [x] Values are always bound, never written into SQL text, so errors and telemetry carry no data ([10](./10-observability.md)). `sql.raw` is for identifiers and constants only; ESLint flags it for review.
- [x] Every read of a soft-deleted table states its filter inline in its query (e.g. `isNull(t.revokedAt)`), including expiry where the table has one (e.g. `gt(t.expiresAt, now)` for sessions), and procedure tests cover it. Drizzle has no global scopes, so a hidden default couldn't be enforced (like Rails' `discard`, not Laravel's `SoftDeletes`).

## Decisions

- Procedures are plain functions taking the database as their first argument: `closeUser(db, { closedBy, closedReason, userId })`. Routes, remote functions, and CLI scripts call the same function with their own client, and tests pass `createTestDatabase()` ([11](./11-testing.md)). They never import `$app/*`, so `cli/` can import them (checked by `tsc -p cli`). Domain verbs name them (`closeUser`, `grantRole`, `revokeRole`). Rejected: repository modules bound to a client at import (they'd pull in `client.ts`, which `cli/` and tests can't import); per-route `server.ts` (CLI can't share it).
- Procedures live in their prefix folder's `procedures.ts` ([05](./05-database.md)), placed by target: the row the caller identifies by ID. `closeUser(db, { userId, … })` is in `user/procedures.ts`, though it also deletes `login` rows; a later `completeLogin(db, { loginId, … })` would be in `login/`. A procedure with no single target (the purge job, [12](./12-operations.md)) gets a folder named after the process (`cli/db/app/purge/procedures.ts`, since only the CLI runs it). Rejected: placing by the tables touched (most procedures span prefixes).
- Named queries: SvelteKit server modules and procedures call queries by name and never build one, so each query has a name, a place, and the soft-delete filter it states ([05](./05-database.md)). Procedures keep the logic (guards, the clock, cascades, which contact to erase) and pass values in; queries hold the SQL. A read takes `db: AppDbOrTx` (`AppDb | AppTx`), so a remote file can call it with `db` and a procedure with `tx`. A write takes `tx: AppTx`, and SvelteKit server modules (remote functions, server hooks, server endpoints, server load functions) can't open a transaction, so every write runs in a procedure: two writes can't half-succeed in a route, and a cascade step (`closeActiveUser`) can't run without its cascade. Queries are placed by the tables they act on, in that prefix folder's `queries.ts`, whoever calls them: `user/queries.ts` holds every `user*` query, and `deleteUserLogins` is in `login/queries.ts`, though `closeUser` calls it. So a prefix's schema, queries, and procedures sit together, and a query never moves when a second caller appears. A route's own queries go in a `queries.server.ts` next to its remote file (`.server`, since `server/` folders under `src/routes` aren't server-only), imported through `#routes/*` (added with the first one, [02](./02-cli-separation.md)). Queries a procedure uses are tested through the procedure's tests; others get a test file next to them, with `createTestDatabase()`. Domain verbs name them too, with a narrowing state in the name (`findActiveUser`, `revokeActiveUserSessions`). The keys show what a query filters by, so `By<Field>` is added only when two queries would otherwise share a name, and then to all of them (`findActiveUserById`, `findActiveUserByContact`); a new clash renames the existing query. Adding a filter doesn't rename one. Rejected: `By<Field>` on every lookup (the name repeats the keys, and a new filter renames every caller).
- CLI-only code mirrors `src/db/`: `cli/db/[database]/[prefix]/` (no `server/`, since all of `cli/` is) holds queries and procedures only CLI scripts call, e.g. the purge job's, so SvelteKit can't reach them. `src/` can't import `#cli/*` (ESLint, [02](./02-cli-separation.md)). The same rules apply: CLI scripts are like SvelteKit server modules (named queries only, no `db` properties), and `cli/db/*/*/procedures.*` like procedures. A query or procedure moves to `src/db/` once SvelteKit needs it, like a route's `queries.server.ts`. Rejected: CLI-only code in `src/db/` (SvelteKit could import it); `_`-prefixed procedure-only queries flagged by `importNamePattern` (the `tx` type already gates writes, a rule can't say "same folder" when cascades cross prefixes, and the name changes with a second caller).
- ESLint enforces it for SvelteKit server modules, CLI scripts (`cli/**` except query files, `client.ts`, drizzle-kit configs, `canary.ts`, and `shared.ts`), and procedures in `src/db/*/server/*/` and `cli/db/*/*/` (tests excluded). They (`svelteKitServerModuleGlobs`) use SvelteKit's own names: remote modules (`src/**/remote.*` and `src/**/*.remote.*`, matching `/[/.]remote\.[^/]+$/`), route modules under `src/routes` (`+server`, and `+page.server`/`+layout.server` with an optional `@group`, matching its `module_name_pattern`), and `src/hooks.server` (a file, or a folder's `index`), each `.js` or `.ts` (`moduleExtensions`). Universal `+page.ts`/`+layout.ts` and `src/hooks.ts` aren't included, since they also run in the browser, where `#db/*/server/…` fails the build ([05](./05-database.md)). `@typescript-eslint/no-restricted-imports` bans value imports of `#db/*/server/schema.ts`, each prefix's `schema.ts` (and a split `schema/`), `drizzle-orm`, and its subpaths (`drizzle-orm/sql` exports the operators too), with types still allowed for `Pick<UserSelect, …>`. `no-restricted-properties` bans every property of `db` in SvelteKit server modules, `transaction` included, and every property of `db` except `transaction` and of `tx` in procedures, since `db.run('…')` takes raw SQL strings and `db._.relations` exposes the tables without an import; it's set in two blocks (SvelteKit server modules, procedures), and each repeats the global `sql.raw` entry, since a block's options replace the global ones. The typescript-eslint rule is separate from core `no-restricted-imports`, so the global bans still apply. `group` globs escape the leading `#` (`\#db/…`), since gitignore syntax reads it as a comment and the pattern would silently match nothing. Left to review: aliasing the client (`const d = db`), since the rule matches by name. Rejected: `db.transaction` in SvelteKit server modules (one chaining writes is a procedure in a route file, and its `tx` would reach the write queries); all queries in `queries/` (a prefix's SQL sits away from its schema and procedures); bound query sets (binders, reserved keys, a rebound `transaction`, and `runProcedure`: a lot of machinery for the same goal); an opaque database handle unwrapped by `defineQuery` (a wrapper on every query, and still needs a lint rule for the import); a type-aware custom ESLint rule (a rule to maintain); a tsconfig per glob (SvelteKit generates one tsconfig, used by `svelte-check` and the editor); a convention without enforcement.
- Queries aren't private to their folder: any file imports them by subpath (`#db/app/server/user/queries.ts`), so there's no exception to subpath imports. The types cover what privacy did: SvelteKit server modules have no `tx`, so they can't call a write, and a procedure calling another prefix's write is a cascade it states. Rejected: procedure-only queries in their folder, imported as `./queries.ts` with the subpath import banned (a second place for each prefix's queries, a move when a query is shared, and the one `./` exception), once writes took `tx`.
- `src/db/app/server/database.ts` holds what every client shares: the `AppDb` and `AppTx` types and `createDatabase(client)`. The SvelteKit client, `createTestDatabase`, and later the CLI client all call it, so tests run the same `transaction` as the app. Test databases migrate through a plain Drizzle instance on the same connection, since `migrate()` needs Drizzle's own class type.
- `db.transaction(callback, { behavior: 'immediate' })`: `AppDb` replaces Drizzle's signature, so the config is required, only `immediate` type-checks, and an async callback is a type error (`T extends PromiseLike ? never`, like Drizzle's own for sync drivers). `createDatabase` only casts Drizzle's client to `AppDb`; nothing is checked at runtime. Immediate, since every procedure reads before it writes, and a deferred transaction lets another writer slip in between (or fails with `SQLITE_BUSY` on upgrade, which the busy timeout doesn't retry). Left to review, since the type can't see them: a callback typed `any` or `unknown` that returns a promise (it would commit at its first `await`, and later statements would run outside the transaction), and casts. Rejected: runtime assertions in a wrapper (an `isPromise` check and a behavior check, for cases typed code rarely reaches); a `transaction(db, callback)` helper with ESLint flagging direct `.transaction()` calls; defaulting to `immediate` silently (the call site wouldn't show it).
- Parameters: one flat object after the client, even for one field, destructured in the signature: `closeUser(db, { closedBy, closedReason, userId })`. An ID key is named after its target (`userId`, `userRoleId`), never `id`, so a swapped ID shows at the call site (`{ userRoleId: userId }`); other keys are column names. Each key's type comes from its table's `Select` type, one field at a time (`closedBy: UserSelect['closedBy']`), so types follow the schema. `Select`, because every column is a required key there: `Insert` would make a nullable column like `closedBy` optional, and a left-out key is `undefined`, which Drizzle skips instead of writing `null` (the system). A column that must not be `null` here uses `NonNullable<…>`, and a narrower value its own type (`revokeRole` takes `revokedReason: UserRoleRevokeReason`, without `cascade_` reasons, [05](./05-database.md)). Values the procedure derives (the clock, a cascade's actor and reason, foreign keys) aren't parameters, so `closeUser` touches six tables but takes three keys; queries take them (`closeActiveUser(tx, { closedAt: now, … })`). Non-column arguments (a viewer, a `SQL` filter) keep their own types. Rejected: one parameter per table typed as a `Pick` (`user: Pick<UserSelect, 'id' | …>`, read as `user.id`; it fixes the key as `id`, and needs type-fest's `SetNonNullable`/`SetFieldType` for narrower fields); a positional value for one field (`findActiveUser(db, userId)`; the call site doesn't label it, and the shape would change when a second field is added); branded ID types (casts at every URL, form, and fixture boundary); `Insert`-based types (see above).
- Procedures take `db: AppDb`, open one transaction, and read the clock inside it (`new Date()`, so tests use fake timers), passing it to queries (`revokedAt: now`). Writes, including steps shared between procedures, are queries taking `tx: AppTx`, so the type requires a caller's transaction, e.g. `deleteUserLogins(tx, { contact, userId })`. `login/queries.ts` keeps a private `deleteLoginsWhere(tx, where)`, which deletes `login_attempt` rows first, then `login`, each its own statement ([05](./05-database.md)); the purge job ([12](./12-operations.md)) gets its own export there. `AppTx` omits `transaction`, so savepoints don't type-check. Rejected: shared steps as procedures (they'd build queries), nesting via savepoints (the inner one would read its own clock, and a no-op couldn't tell the caller to stop).
- Guards: a procedure checks every row it depends on inside its transaction (target user active, actor active unless `null`, role active or not) and returns falsy without writing when one fails: `false`, or `undefined` where it returns an ID. Updates also repeat `isNull(…At)` in their `WHERE`, so a final group is never overwritten ([05](./05-database.md)). Authorization (is the actor an admin?) stays in routes ([08](./08-auth.md)): procedures also serve the CLI, where the actor (`closedBy`, `assignedBy`, …) is `null`. Each guard has a test that checks the return value and that nothing changed.
- `closeUser` implements [08](./08-auth.md)'s closing: it revokes active roles and unexpired sessions with `cascade_user_closed` and the triggering actor, deletes the profile and the logins matched by user ID or contact, and erases the contact unless banned. Expired sessions stay as they are: they're already invalid, and the purge job deletes them.
- Soft-delete filters are written inline in each query (`isNull(t.revokedAt)`, plus `gt(t.expiresAt, now)` for sessions). `where` filters put one condition per line, so the soft-delete filter stands out; a trailing `//` after the first keeps the formatter from joining short ones. Procedure tests seed revoked and expired rows next to active ones and check that they're left alone.
- Sync API only: queries end in `.run()`, `.all()`, or `.get()`. ESLint flags `await` under `src/db/` (Drizzle's builders are thenable, so `await` would also work, but async code can't run inside a transaction). Insert `.get()` is fine since 1.0.0-rc.5: it types as `T | undefined` when the insert may return no row, e.g. with `onConflictDoNothing()` ([drizzle-team/drizzle-orm#6107](https://github.com/drizzle-team/drizzle-orm/issues/6107)).
- Audited reads: not built yet, since there's no audit logger until [07](./07-audit-logging.md). Planned shape: queries and procedures take their client as an argument, so a route opts in per call by passing an audited client instead of `db`. The box stays open until then.
