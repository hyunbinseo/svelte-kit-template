# 10 Observability

Sentry for client, server, and CLI, with privacy-first data collection.

## Ideas

- Share init between client and server.
- Check whether SvelteKit offers a cleaner hook for validation errors.

## Checklist

- [x] Disabled in development and when `SENTRY_DSN` is unset.
- [x] One data-collection config applied everywhere: no user info beyond the internal user ID, IPs, cookies, bodies, URL query params, or DB query params; forwarding/IP headers denied. SQL text with placeholders is allowed: it's how DB errors get debugged, and SQLite's error messages hold no values ([05](./05-database.md)).
- [x] Traces sampled (not 100%).
- [x] CLI uses `@sentry/node`, never `@sentry/sveltekit` (see [02](./02-cli-separation.md)).
- [x] Requests tagged with user ID when logged in (server and client).
- [x] Remote function validation errors logged as warnings with issue paths only, no values.
- [x] A Sentry setup guide (project, DSN, source maps, alerts).

## Decisions

- `@sentry/sveltekit` and `@sentry/node` 11, and `@standard-schema/utils`, as devDependencies like every other package (adapter-node bundles the server; the CLI imports `@sentry/node` at runtime, as it does `vite` and `valibot`, [02](./02-cli-separation.md)).
- One options object, `sentryOptions` (`src/lib/sentry/options.ts`, CLI-safe), spread into all three `init` calls, which add only `dsn`, `environment` (the mode), and `release`. SvelteKit's additions live in `src/lib/sentry/kit.ts` (`sentryKitOptions`, and `isSentryEnabled`, which the server, client hooks, and root layout share); the CLI can't import it (`$app/*`). It uses SDK 11's `dataCollection`, which replaces `sendDefaultPii`: `userInfo: false` (no IPs or inferred user fields; the browser SDK also tells Sentry not to infer the IP), and no cookies, bodies, query params, DB query data, stack frame variables, or GraphQL, AI, MCP, and queue payloads. Headers are allowlisted to `User-Agent` (browser and OS); the rest are sent as `[Filtered]`, so a header added later (e.g. a new proxy's IP header) can't leak. Sentry's defaults sent `x-forwarded-for`, `x-real-ip`, and `referer` with its query on spans, even with `userInfo: false` (verified on 11.11). Console breadcrumbs are dropped (`beforeBreadcrumb`): console output can hold values, e.g. a failed parse's input. Rejected: a denylist of forwarding and IP headers (misses headers it doesn't know); `httpHeaders: false` (loses the browser and OS); `beforeSend` scrubbing per field (`dataCollection` covers every integration).
- Verified against a local mock ingest with a DSN build: a logged-in request with query params, a cookie, `X-Forwarded-For`, `X-Real-IP`, and `Referer`, a 404, a remote query validation failure, and server and client errors. The envelopes held none of the values (query params, IPs, cookie values, the session token, the contact, or submitted input), only the user ID. Paths like `/account` are always sent. After the switch to a header allowlist, a rerun showed every header but `user-agent` as `[Filtered]`, including an unknown `X-New-Proxy-Client`.
- Disabled in development (`dev` in SvelteKit, `MODE=development` in the CLI) and when `SENTRY_DSN` is unset. Other modes send, with `environment` set to the mode, so an e2e build with a DSN reports as `e2e`.
- Server: `src/instrumentation.server.ts` calls `init`, which SvelteKit loads before the app. `src/hooks.server.ts` runs `sentryHandle()` first in a `sequence`, so each request has its own isolation scope, then tags it with `setUser({ id })` after `handleSession`. SvelteKit's own tracing (`tracing.server`, already on) supplies the spans, so the Vite plugin's `autoInstrument` is off.
- Client: `src/hooks.client.ts` imports the SDK statically and calls `init` only when enabled; `handleErrorWithSentry()` is always the `handleError` hook (it logs like SvelteKit's default, and captures nothing before `init`). The bundle keeps Sentry with the DSN unset (about 20 KB gzipped): a static import inside `if (isSentryEnabled)` isn't dropped, since the bundler can't see across modules that `SENTRY_DSN` is `undefined`. Accepted: a project that sets a DSN loads it anyway. Rejected: a dynamic import in the `init` hook (drops it when unset, but delays hydration by a request when set). The root layout tags the client with `getSessionUserId` (`src/routes/remote.ts`, which also replaces the home page's `getIsLoggedIn`), in an effect that SvelteKit refreshes after the login and logout forms, and skips the query when disabled. Rejected: a root `+layout.server.ts` returning the user ID (the prerendered home page bakes in `undefined`, and client navigation from it doesn't rerun the load); reading it in each logged-in layout (misses other pages).
- Errors: `handleErrorWithSentry` captures unknown errors and 5xx, and skips 4xx and validation errors. Its wrapped handler logs unknown errors like SvelteKit's default. Remote function validation errors are logged as warnings (`console.warn` and a `warning` event) with issue paths only (`getDotPath` from `@standard-schema/utils`, `null` for an issue without one): SvelteKit's default logs whole issues, whose messages and inputs hold submitted values. SvelteKit 3 passes them to `handleError` (`kind: 'validation'`); there's no separate hook. The audit logger's `report` ([07](./07-audit-logging.md)) and the login code sender's failure also call `captureException`, after `console.error`.
- CLI: `cli/lib/preload.ts` initializes `@sentry/node` after loading env files, so every script reports uncaught errors (`fatal`, exit code 1; verified with a mock ingest). `@sentry/sveltekit` declares SvelteKit's types, so importing it from `cli/` fails `cli/canary.ts` ([02](./02-cli-separation.md); verified). No release: reading the commit SHA would need `git` in the release directory, which `app` may not be allowed to run.
- Sampling: `tracesSampleRate: 0.1`. Raise it for low-traffic projects.
- Build: `sentrySvelteKit` (before `sveltekit()` in `vite.config.ts`) uploads source maps only when `SENTRY_AUTH_TOKEN` is set, then deletes them from `build/`. The release is the commit SHA SvelteKit's `version.name` already uses, and `init` reads it from `$app/env`'s `version`. Plugin telemetry is off. Setup steps: `docs/sentry.md`.
- Importing `$app/env/public` in `src/instrumentation.server.ts` runs `src/env.ts` (and Valibot) before instrumentation starts, so those can't be instrumented. Accepted: nothing there needs it.
